## 1. What does the organiser dashboard show and do today, screen by screen, and which parts are only dummy data in localStorage?

### Takeaway
The dashboard is a fully client-side demo: 5 nav items, 6 routes, no network calls; identity, role status (including self-approval), created events, and all numbers on screen come from localStorage (`ga.demo.v1`) or hardcoded constants in `sample.ts`. Only one thing the user does is persisted (an event "stub" with 5 fields written to localStorage); nothing reaches Supabase or NestJS.

#### Mobile behaviour
- < 900px: sidebar becomes a fixed bottom tab bar (icon + 11.5px label, min-width 68px, horizontally scrollable, safe-area padding), `padding-bottom: 92px` on shell; hover-less — [portal.css:7-17](FE/components/portal/portal.css). Dashboard top bar (org name + switcher) scrolls with the page.
- `DataTable` < 640px: header visually hidden, each row becomes a stacked card with `data-label` captions — [portal.css, @media max-width 639px block, `.rd-table`](FE/components/portal/portal.css). Defect: `td[data-minor]` is `display: none` at that width (e.g. Registrations "Bib", Events "Registered", Payouts "Period"), while the code comment says "Hidden on narrow screens (the row still shows it in the stacked card view)" — [DataTable.tsx:15](FE/components/portal/DataTable.tsx) vs. CSS rule `.rd-table td[data-minor] { display: none; }`. So on phones an organiser cannot see bib number or registered/capacity in the list.
- Charts use `viewBox` + `preserveAspectRatio="none"` (line chart) so text labels can stretch on very narrow/odd widths — [charts.tsx:20](FE/components/portal/charts.tsx).
- No phone-oriented race-day tooling (scan/check-in) exists; the only phone-first feature is layout.

### Inferences
- The user-visible organiser "product" is a prototype of layout and flow only. Anything an organiser would actually need on race day or sales day (publish, view real attendees, check in, export, pay out) is not wired to data.
- Overview numbers are internally inconsistent by construction (e.g., donut totals 1,620 vs "Registrations" KPI sum of events; check-in rate string is not derived), so any real build must replace them rather than adapt them.
- Because the guard and approval live in localStorage, the demo can be used to test UX but cannot be used to test organiser permissioning at all.

## 2. Which backend/database pieces already exist that the dashboard could use immediately, and which are missing?

### Takeaway
The database already models most of an organiser's data (events with setup fields, ticket types, waves, form fields, tickets with QR, participants, answers, orders, payments, refunds, coupons, payouts, broadcasts, staff, stats, results, KYC) with RLS that lets organiser admins and event staff read it, plus two service-role-only SQL functions (`create_registration`, `search_participants`). The NestJS backend, however, exposes only public read endpoints and one public booking endpoint; there is no organiser guard, no organiser-facing endpoint of any kind, and no write path for events, form fields, check-in, payments, exports, comms or payouts.

### Cited Findings

#### NestJS surface today (the whole HTTP API)
- Modules in `AppModule`: Config, Prisma, Supabase, Events, Taxonomy, Auth, Registrations — [src/app.module.ts:1-24](BE/src/app.module.ts)
- Endpoints: `GET /events`, `GET /events/:id/details`, `GET /events/:id` (public) — [events.controller.ts:5-24](BE/src/events/events.controller.ts); `GET /taxonomy/sports` — [taxonomy.controller.ts:4-12](BE/src/taxonomy/taxonomy.controller.ts); `POST /registrations` (public, 201) — [registrations.controller.ts:5-14](BE/src/registrations/registrations.controller.ts); `GET /me` guarded by `SupabaseAuthGuard` — [me.controller.ts:18-41](BE/src/auth/me.controller.ts)
- `SupabaseAuthGuard` only validates a Bearer token via `supabase.auth.getUser` and sets `{id,email,phone}`; it checks no role, organiser membership or event ownership — [supabase-auth.guard.ts:22-52](BE/src/auth/supabase-auth.guard.ts). `/me` returns only profile name/avatar/onboarding flag, not organiser membership or account type.
- A grep for `@Get/@Post/@Patch/@Put/@Delete` showed no other controllers (only the files above exist under `src/`).

#### Registration booking (exists, public)
- `POST /registrations` loads the event (must be `visibility = public`, `publication_status = published`, `ticketing_mode = platform`; registration window; not completed/cancelled), loads categories, price tiers and `event_form_fields`, validates per-order limit, age and gender, answers vs. organiser fields, computes price/GST, QR tokens, then calls `create_registration(p jsonb)` — [registrations.service.ts:70-130,207](BE/src/registrations/registrations.service.ts). Private/unlisted events cannot be booked yet (open item in [Registrations data model.md:97](BE/02 Architecture/Registrations data model.md)).
- Orders are created `pending_payment` and tickets `reserved`; "Payments are not live (ADR-007)" — [registrations.service.ts:60-64](BE/src/registrations/registrations.service.ts). No code creates `payments` rows or confirms tickets.
- `create_registration` inserts order, participants, tickets (with `qr_token`, `qr_payload`, `qr_svg`), and `registration_answers` in one transaction, with `SOLD_OUT`/`BAD_CATEGORY` errors and idempotency key; EXECUTE granted to `service_role` only — [20261112000027_registrations.sql:6 sections 6 and 7 (function body ~lines 148-232; grants at end)](BE/supabase/migrations/20261112000027_registrations.sql)
- `search_participants(event, query, limit)`: substring/trigram search over name/email/mobile, exact on ticket number, bib or QR token; returns ticket id, number, bib, status, category, participant, name, email, phone, order number, score; limit capped at 100; service-role only. Doc: ~1 ms warm at 100,000 participants; "There is **no HTTP route for search yet, on purpose**" — [0027:~244-272](BE/supabase/migrations/20261112000027_registrations.sql), [Registrations data model.md:56-73,84](BE/02 Architecture/Registrations data model.md)

### Inferences
- The lowest-friction data for a first real dashboard slice is: attendee list + search + sensitive-aware answers (tables and `search_participants` exist), event/ticket-type read (RLS already allows organiser admin reads), and payout history (table exists, but would be empty until a settlement process runs). Each still needs an authenticated, organiser-scoped API (or Supabase client with RLS) because only a NestJS guard or RLS can enforce organiser scoping and the only existing guard doesn't.
- Two paths exist for organiser reads: direct Supabase client under RLS (policies already written for tickets, participants, answers, payouts, broadcasts, coupons, stats) or NestJS with a new `OrganiserGuard`. ADR-007 warns that the NestJS backend uses the service role and bypasses RLS, so every query must filter explicitly (ADR-007:54-56); this argues for either RLS-first reads or a very careful guard plus event-ownership checks.
- Organiser-originated writes (events, categories, form fields, waves) have no policy and no endpoint, so the "Create event" flow cannot persist until one of them is added.
- Revenue figures on a real dashboard can't be correct until payments are live: orders stay `pending_payment` and tickets `reserved`, so "confirmed", "checked-in" and "revenue" metrics would currently be zero.

## 3. What are the top usability, accessibility and structural weaknesses in the current dashboard?

### Takeaway
Structurally, the dashboard is a thin, event-agnostic list-and-chart shell: no event workspace, no task flow, no real-time or race-day tooling, and shared generic components reused across roles. Accessibility foundations are decent (labelled nav, `aria-current`, table caption, labelled search, error roles, reduced-motion handling) but there are specific defects in data tables on mobile, charts, menu semantics, locked-page navigation, and the demo approval control. Usability weaknesses are mostly missing capability and misleading sample data.

### Cited Findings

#### Structural weaknesses
- No event-scoped workspace or IA: navigation is flat by object type (Events, Registrations, Payouts) rather than by event or job-to-be-done; Registrations mixes all events in one list with no event selector — [nav.ts:20-26](FE/components/portal/nav.ts), [OrganiserPages.tsx:79-96](FE/components/portal/OrganiserPages.tsx). The product doc's reference console uses a per-event workspace plus race control, marketing, finance and settings groups — [Organizer and seller platform features.md:11-61](BE/01 Product/Organizer and seller platform features.md).
- One generic page component per role family and shared `PayoutsPage`/`SettingsKyc`/`CreatePage` across organiser, seller and coach, with role differences handled by a numeric `SCALE` multiplier and a `CONFIG` map — [CommonPages.tsx:23,119-136](FE/components/portal/CommonPages.tsx). Organiser-specific needs (per-event settlements, TDS/TCS, GST invoices) don't fit this shape.
- Data access is hardcoded inside page components (`useEvents()` concatenates `items.events` and `EVENTS`; pages import `sample.ts` directly), no data-fetching layer, no loading/error contract, no types shared with the backend — [OrganiserPages.tsx:14-17](FE/components/portal/OrganiserPages.tsx), [sample.ts:1-10](FE/lib/demo/sample.ts). `CreatedRow` is `Record<string,string|number>` cast to `EventRow` via `as unknown as` — [OrganiserPages.tsx:16](FE/components/portal/OrganiserPages.tsx), [types.ts:40](FE/lib/demo/types.ts).
- The Overview donut and KPI values are literals or mixed (sample + created) data; the chart components take display-ready arrays, so any real build must provide aggregation endpoints (e.g., by category) — [OrganiserPages.tsx:46-47](FE/components/portal/OrganiserPages.tsx).
- Account model drift: the shell still treats an organiser as one role of a person with a role switcher and "Athlete view" link, while ADR-010 says each role is its own account — [RoleSwitcher.tsx](FE/components/portal/RoleSwitcher.tsx), [ADR-010:29-39,54-57](BE/03 Decisions/ADR-010-separate-accounts-per-role.md).
- Approval gating is cosmetic and based on nav-level "locks"; gating is by page, not by action, and published-event actions are not distinguished from read-only access — [PortalShell.tsx:72,104](FE/components/portal/PortalShell.tsx).
- Footer/marketing chrome suppression relies on a CSS `body:has(.rd-shell) main ~ section ...{display:none}` rule rather than a layout boundary — [portal.css:4](FE/components/portal/portal.css).
- Only a single global status per role: there is no notion of per-event readiness (the DB has a publish gate with specific missing items, `check_event_publishable`, whose error lists missing fields) — [0023:272-322](BE/supabase/migrations/20261001000023_event_setup.sql); the UI has no place to show "what's missing to publish".

#### Usability weaknesses
- No row actions or detail views: Events and Registrations rows cannot be opened, edited, exported or acted on — [DataTable.tsx:72-77](FE/components/portal/DataTable.tsx).
- Create event is a stub: price, description and venue are validated then discarded; no ticket categories; date entered as free text `YYYY-MM-DD` instead of a date picker; created events are stuck as drafts with no publish step — [forms.ts:5-28](FE/lib/demo/wizards/forms.ts), [CommonPages.tsx:122](FE/components/portal/CommonPages.tsx), [wizards/types.ts:51,55 (date format message/regex)](FE/lib/demo/wizards/types.ts).
- No next-best-action / checklist on Overview for an active organiser (no "finish your draft", "N payments pending", "event in 3 days"); only a generic "Create event" button — [OrganiserPages.tsx:29](FE/components/portal/OrganiserPages.tsx).
- No time-range control: Overview's "last 12 weeks" and "vs last 4 weeks" are fixed — [OrganiserPages.tsx:29](FE/components/portal/OrganiserPages.tsx), [ui.tsx:52](FE/components/portal/ui.tsx).
- No bulk actions, no saved views, no column sort (DataTable has search + one status filter only), no pagination or virtualisation (it filters the whole array in memory) — [DataTable.tsx:31-81](FE/components/portal/DataTable.tsx). The DB is built for 100,000 participants per event (data model :84), so the current table design would not scale to real attendee lists.
- Misleading sample data: "Check-in rate 87%" with no check-in feature; payouts labels mix scheduled/processing states as "Available balance"/"In transit" — [OrganiserPages.tsx:34](FE/components/portal/OrganiserPages.tsx), [CommonPages.tsx:93-96](FE/components/portal/CommonPages.tsx). A "DEMO" banner exists only on the approve button; the data screens carry only a small "Sample data" sub-title (Overview, Registrations, Payouts), not on Events.
- Locked pages: three of five nav items are locked until approval, and the lock screen is the only content on those routes (no preview of what they will contain) — [PortalShell.tsx:104-106](FE/components/portal/PortalShell.tsx). Note that lock reasons are inconsistent: Events says KYC; Registrations says "an active organiser account" although both use the same `active` flag — [nav.ts:22-23](FE/components/portal/nav.ts).
- No help/onboarding path for first-time organisers (the product doc mentions a "Playbook" checklist module) — [Organizer and seller platform features.md:19](BE/01 Product/Organizer and seller platform features.md).
- Search is client-only substring match across the columns that define `text`; Events search does not include status/revenue; Registrations "Search name, event or bib" placeholder also matches city and category (benign) — [OrganiserPages.tsx:64,84,87-89](FE/components/portal/OrganiserPages.tsx).
- `DataTable` filter pills render raw lowercase option text via CSS `text-transform: capitalize`; "all" is hardcoded; filter state resets on unmount (not in URL), so back-navigation loses search/filter — [DataTable.tsx:32-33,55-57](FE/components/portal/DataTable.tsx).

#### Accessibility issues observed in code
- Mobile table cards hide "minor" cells (`display:none`), removing information from sighted and screen reader users on phones; contradicts the code comment — [portal.css `.rd-table td[data-minor]` in max-width 639px block](FE/components/portal/portal.css), [DataTable.tsx:15](FE/components/portal/DataTable.tsx).
- In the mobile card view, `thead` is clipped (visually hidden) and the table is switched to `display: block` on `table/tbody/tr/td`, which in several browsers drops table semantics for assistive tech (known behaviour of `display` overrides); cells keep `data-label` via CSS `::before` content, which is not reliably exposed as an accessible name — [portal.css max-width 639px block](FE/components/portal/portal.css). (Known browser behaviour, not tested here.)
- Charts: the line chart is an `svg role="img"` with an aria-label (good) but individual `<title>` per data point inside an `img` role is not accessible to screen readers, and there is no table/text alternative with the underlying numbers; the donut has no per-segment values in the accessible name (list is visible but the svg is `role=img`); colours are fixed hex literals (`#12B4A0`, `#6FCB1A`, `#F2B134`, `#8A91AD`) with no dark-mode adaptation or non-colour encoding in the donut/line — [charts.tsx:20,30,62-67](FE/components/portal/charts.tsx), [OrganiserPages.tsx:47](FE/components/portal/OrganiserPages.tsx). The BarList bars are `aria-hidden` with numeric text alongside (good) — [charts.tsx:47-48](FE/components/portal/charts.tsx).
- Line chart uses `preserveAspectRatio="none"`, so SVG text (axis labels) distorts when container aspect ratio differs; labels are 12 weeks with only every other label shown, and no y-axis labels or units at all — [charts.tsx:20,28-31](FE/components/portal/charts.tsx).
- `RoleSwitcher` uses `role="menu"` / `role="menuitem"` on links, with Escape and click-outside support but no arrow-key navigation or focus return found in the lines read — [RoleSwitcher.tsx:32-35,43-56](FE/components/portal/RoleSwitcher.tsx). A `menu` role promises arrow-key behaviour that links don't provide (ARIA authoring practice); a disclosure pattern would be more accurate.
- Page title: `metadata.title` is static "Organiser dashboard - GoAthletix" for every organiser route (layout-level), so browser tab / screen reader announces the same title on every page — [app/organiser/layout.tsx:5-8](FE/app/organiser/layout.tsx). The `PageHeader` renders an `h1` per page (good) — [ui.tsx:22-32](FE/components/portal/ui.tsx).
- Route change focus: no skip link or main landmark is rendered by the shell (the content wrapper is a `div.rd-content`, not `<main>`; `.rd-main` is also a div); the nav is a `<nav>` with a label (good) — [PortalShell.tsx:78,95,107](FE/components/portal/PortalShell.tsx). The `<main>` is presumably in the root layout (CSS refers to `main ~ section`), which was not read.
- Status is conveyed by chip colour plus text (good); `rd-chipx` colour contrast tokens not verified. KPI delta direction is communicated by icon + text with `data-up` styling (colour) and arrow icons marked `aria-hidden`; the trailing "% vs last 4 weeks" text does not say "up" or "down" — [ui.tsx:49-54](FE/components/portal/ui.tsx).
- Status banner uses `role="status"` which is polite but is inserted on every page for non-active accounts and contains the primary actions — [PortalShell.tsx:44](FE/components/portal/PortalShell.tsx). The `LockedState` also uses `role="status"` with an `h2` — [ui.tsx:88](FE/components/portal/ui.tsx); it replaces the page `h1`, so locked pages have no `h1` (the header is not rendered when locked) — [PortalShell.tsx:104-108](FE/components/portal/PortalShell.tsx).
- Bottom tab bar on phones: labels at 11.5px, bar is a horizontally scrolling `nav` with hidden scrollbar; five items at min 68px each (340px) fits a 360px phone only tightly and relies on scroll on narrower screens; touch targets are >= 44px high only on desktop (`min-height: 44px` set only in the >= 900px block) — [portal.css:8-12,23](FE/components/portal/portal.css).
- Positive findings: `aria-current="page"` on the active nav link; `DataTable` has a visually hidden caption, a labelled search input (`sr-only` label), `role="group"` filter with `aria-pressed` buttons, and `aria-live="polite"` count; wizard fields have `aria-invalid`, `aria-describedby`, `role="alert"` errors, and focus to first invalid field; `Reveal` honours `prefers-reduced-motion` and the CSS disables skeleton animation for reduced motion — [DataTable.tsx:48-60](FE/components/portal/DataTable.tsx), [FieldRenderer.tsx:17-20](FE/components/wizard/FieldRenderer.tsx), [ui.tsx:35-41](FE/components/portal/ui.tsx), [portal.css prefers-reduced-motion rule](FE/components/portal/portal.css).
- Keyboard: filter buttons have focus-visible rings; the wizard's field `Input` focus style removes outline in `.rd-search-in:focus { outline: none; ... box-shadow }` replaced by a coloured border and shadow (acceptable if contrast holds; not verified) — [portal.css `.rd-search-in:focus`](FE/components/portal/portal.css).
- Select-like "cards" and "chips" in forms use `role="radio"`/`role="checkbox"` on `<button>`s without explicit arrow-key handling for radiogroup in the lines seen — [FieldRenderer.tsx:37-53](FE/components/wizard/FieldRenderer.tsx).

#### Security / trust weaknesses relevant to a real build
- The dashboard's authorisation is purely client-side and bypassable, and self-approval exists; sensitive-data handling (PAN, bank number) is "secret" masked in the UI but stored in plain localStorage — [store.ts:7,44](FE/lib/demo/store.ts), [organiser.ts:35](FE/lib/demo/wizards/organiser.ts). The code itself says nothing is verified or sent anywhere.
- Real KYC fields in DB are guarded by trigger and RLS; none of that is connected — [0022 section 2](BE/supabase/migrations/20261001000022_ticketing_private_events.sql).

### Inferences
- The highest-value structural fix is an event-scoped workspace (event overview, tickets, form, attendees, check-in, comms, money) because every DB table that matters is keyed by `event_id` and organiser access is derived from `events.organizer_id`; the current flat nav can't express that.
- Attendee lists need server-side search/pagination (backed by `search_participants` and the indexes) rather than the in-memory `DataTable`.
- A first accessibility sweep should target: mobile table cards (show all essential fields), chart text alternatives, menu semantics (switch to disclosure or remove the switcher per ADR-010), a `<main>` landmark/skip link and per-page titles, `h1` on locked pages, and touch target size on the mobile tab bar.
- Because sample numbers appear alongside real-looking UI (check-in 87%, payouts), the current screens would mislead anyone shown them as functionality; any demo build should visibly label data as sample on every screen (including Events and Settings).

- No screen reader or keyboard run-through; browser/AT behaviour of `display: block` tables is stated from known behaviour, not tested here.
- Did not read `BecomeRole.tsx`, `/organisers` landing, `Stepper`/`wizard.css` styles in full, or `RoleSwitcher` below line 56, so keyboard behaviour of those is not fully assessed.
- Did not compare against competitor consoles beyond what the product doc (`Organizer and seller platform features.md`) already records.
